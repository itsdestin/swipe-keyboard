# Keeping Swipe Keyboard working on Plasma 6.9's new keyboard (2026-10-23)

Read-only research plus a throwaway test build. No product code changed. plasma-keyboard
master is commit `030ce04` (2026-10-23). MR !179 (opened the same day) was also tested.
Line references point into that checkout (`~/.cache/swipe-keyboard-train/plasma-keyboard-master`).

## Summary for Destin (plain language)

**What happens if we do nothing.** Plasma 6.9 is due on **23 February 2027** (beta 19 January,
feature freeze 5 January). Its keyboard has been rebuilt from scratch. Our add-on plugs into
the old parts, which are gone, so it will not load at all.
- **Arch/CachyOS:** our package says "needs a keyboard older than 6.9". On upgrade day
  `pacman -Syu` refuses to update the **whole system** until the person removes our package.
  This is the worst outcome, and the cheapest one to fix: one line in our package.
- **Fedora:** the same rule blocks or holds back the keyboard update. The exact behaviour is
  not tested.
- **If the update is forced through anyway:** our launcher notices the unknown version and
  starts KDE's normal keyboard instead. Typing still works, but there is no swipe, no
  suggestions and no learning.
- **Steam Deck Flatpak:** this carries its own copy of the old keyboard, so a Plasma update
  does not affect it.

**Can we make it keep working without asking KDE for anything?** Mostly yes. I tested this
on KDE's newest keyboard code in a test build (never on this computer's keyboard):
- Our add-on can **put its own version of each language's keyboard "in front of" KDE's**. The
  person's existing language choices keep working and still pick up our version. Nothing is
  overwritten, and KDE's settings page still shows the normal list.
- Inside that keyboard our code can **watch every finger**. When a finger slides, the add-on
  takes over the touch: the key underneath types nothing and the add-on types the swiped word.
  A normal tap still types its letter. **Tested, works.**
- It can **replace the last word** (tap-to-swap, picking a completion): **tested, works.**
- It can **turn swipe off in password fields**: **tested, works.**
- It can **add our own suggestion row above the keys**: **tested, works.**

**What we lose without KDE's help:**
- KDE's own suggestion row and the "underlined word being typed" (preedit) are reserved for
  code built **into** the keyboard. An add-on cannot use them. So we draw our own suggestion
  row and type words straight into the app. In apps that don't report their text back to the
  keyboard, fixing an earlier word works less reliably than it does today.
- We cannot add our settings to KDE's keyboard settings page. Our own settings commands stay.
- Everything we hook into is internal to the new keyboard and could change without notice.
  It already did: a change proposed today (MR !179) reorganises how keyboards are described.
  The test above passed on **both** versions, but expect more changes until the January freeze.

**Effort:** about **4–6 weeks** of work for a 6.9 version with today's features, plus
**1 week** testing on the real 6.9 beta in January. Also a **same-day fix now**: stop our
package from blocking system updates.

**Biggest risks:** (1) KDE keeps changing the internals until the freeze, so we would build
twice. Build the core now, finish against the beta. (2) Without KDE's text-composer slot,
word fixing depends on each app reporting its text. (3) Distros may ship 6.9 before we are
ready. The package fix above turns that into "swipe is missing for a while", not "can't update".

## 1. Extension points: what a third-party package can add without patching

| Want to add | Possible without patching? | How it is found |
|---|---|---|
| (a) Text composer (C++ class that receives key presses, sets the underlined word being typed, fills KDE's suggestion row) | **No** | Composers are C++ subclasses of `AbstractTextComposer` (`virtualkeyboard/textcomposers/abstracttextcomposer.h`). It is built into a **STATIC** library (`virtualkeyboard/CMakeLists.txt:4`) inside the `plasma-keyboard` executable (`src/CMakeLists.txt:9,128,132`), with `-fvisibility=hidden` and no `ENABLE_EXPORTS`. Verified: the harness built the same way exports 0 composer/engine symbols (`nm -D`), and the installed 6.7.5 `/usr/bin/plasma-keyboard` exports only 29 Wayland symbols. A plugin cannot link against these classes, and QML cannot subclass a C++ abstract class. |
| (b) Keyboard layout package | **Yes** | `QStandardPaths::locateAll(GenericDataLocation, "plasma/keyboard/keyboardpackages")` (`virtualkeyboard/keyboardlayoutmetadata.cpp:41`). It reads each `<dir>/metadata.json` (KPluginMetaData, `:99`) with `X-Plasma-Keyboard.KeyboardLayouts[]` and `Locales`. Layout QML is any local file at `<pkg>/contents/layouts/<file>` (`keyboardpackageresolver.cpp:74`). Packages install to `/usr/share/plasma/keyboard/keyboardpackages/<Id>` or `~/.local/share/...` (`layouts/CMakeLists.txt:13`, `README.md:32`). **Lookup is first match** (`keyboardpackageresolver.cpp:~111-125`), so a package with the **same KPlugin Id** in an earlier data directory shadows KDE's. |
| (c) Swipe/gesture handler | **Yes, inside (b)** | Layout files are arbitrary QML. They may import any QML module on the import path: `QQmlApplicationEngine` (`src/main.cpp:84`) honours `QML_IMPORT_PATH`. Each key is a `MultiPointTouchArea` (`components/keys/KeyMouseArea.qml:11`). A pointer handler above the keys can take a touch away; the key then gets `onCanceled` and types nothing (`components/keys/Key.qml:111`). Key geometry is plain QML items (`key`, `text`, x/y), readable by walking the layout. |
| (d) Suggestion provider | **Not into KDE's row** | KDE's row (`components/KeyboardStrip.qml`) shows `inputEngine.wordCandidateListModel` and is visible only when candidates exist (`:25`). `InputEngine.candidates` is READ-only (`inputengine.h:41`); `setCandidates`/`setPreeditText` are plain C++ (`:64,68`), so only built-in composers can call them. **Workaround:** draw our own row inside our layout package. |

Engine features a plugin can use with no linking, through Qt's property/method system (`inputengine.h`):
`surroundingText`, `cursorPosition`, `anchorPosition`, `inputMethodHints`, `locale`,
`uppercase`/`shiftActive` (writable), `preeditText` (read), and the invokables
`commit(text, replaceFrom, replaceLength)` (`:89`, which deletes then commits, `inputengine.cpp:293-304`),
`sendTextComposerKey`, `sendDirectKey`, `selectCandidate`, `clear`. `KeyboardController` exposes
`layoutId`, `layoutType` and `activeLayoutIds`. The `VirtualKeyboard.*` attached property
reaches all of them from any item inside the keyboard.

**Needs upstream** (none of it blocks the add-on, but all of it would make it cleaner):
1. Composer plugins: either install `virtualkeyboard` as a shared library with headers, or
   load composers as Qt/KPlugin plugins named in `metadata.json`. This brings back preedit and
   KDE's own suggestion row.
2. A supported place to add a layer above any layout, instead of our wrapper plus tree search.
3. A third-party settings page in the KCM.

The compositor link is unchanged: input-method-v1 plus KWin fake-input (`README.md:10`),
started from a `.desktop` file with `X-KDE-Wayland-VirtualKeyboard=true`
(`src/org.kde.plasma.keyboard.desktop`). So our "Swipe Keyboard" launcher entry still works.

## 2. Design: our add-on on the new core

**Entry point.** Keep today's launcher (`integration/setup.py launch`): pick our private
environment, then `exec plasma-keyboard`. On 6.9 the private data directory holds
**generated shadow packages** instead of patched Qt VKBD layouts:
- For each supported stock package (en, es, fr, de), copy KDE's package into
  `$SWIPEKB_DATA/overlay/plasma/keyboard/keyboardpackages/<same Id>/`. Add one wrapper file
  per letter layout and point that layout's file at the wrapper. Master format:
  `"Files": {"main": ...}`. MR !179 format: `"File": ...`. Handle both.
- Each wrapper is 4 lines: `import SwipeKeyboard; <StockFile> { id: w; Component.onCompleted: SwipeHook.watch(w) }`.
  The stock file stays a same-directory type, so its relative imports keep working.
- `XDG_DATA_DIRS=<overlay>:<system>` puts ours first. KDE's settings page runs without this
  variable, so it lists the stock packages only (no duplicates). The person's saved IDs
  (`org.kde.plasma.keyboard.en/mobile-qwerty`) resolve to our copy. Languages we don't support
  stay stock.
- Regenerate at every launch, under the existing lock and atomic rename (as `layout.py` does
  today). A KDE update then cannot leave a stale copy.

**Component mapping**

| Ours today | On 6.9 | Status |
|---|---|---|
| `plugin/SwipeCapture.qml` (PointHandler plus `virtualKeyCancel`) | New `SwipeLayer.qml` above the layout. A `DragHandler`/`PointHandler` steals the touch past the threshold, so the key gets cancel. | Verified in harness |
| Key geometry (`SwipeLayout`, `setPhysicalLayout`) | Walk the live layout items (`key`, `text`, `mapToItem`). This works for any physical layout and replaces the static tables. | Verified (proto finds keys under the path) |
| Swipe recognition (`engine/` `SwipeEngine`, `swipe_*`, `ownswipe.*`, `swipesession.*`) | Unchanged C++, called from a new QML-facing bridge class (replaces `SwipeInputMethod`) | Inferred (no Qt VKBD in these files) |
| Commit swiped word | `inputEngine.commit(word + " ")`. Apply case ourselves from `uppercase`, then set `shiftActive=false` (`handleKeyCommit` does this only for taps). | Commit verified; case handling inferred |
| Completion while tapping | Taps go through KDE's `BasicTextComposer`, which commits directly. Read the current word from `surroundingText` before `cursorPosition`. When the app gives no text, fall back to listening to each key's `clicked` signal (`Key.qml` emits it after `sendTextComposerKey`). Picking a completion: `commit(word, -bytes(prefix), bytes(prefix))`. | Replacement verified; word-tracking inferred |
| Next-word (`nextwordsession`, `nextwordworker`, n-gram/NWP) | Unchanged; drives our own row | Inferred |
| Suggestion row (Qt VKBD `selectionList*` overrides) | Our `SuggestionStrip` inserted as the **first row** of the layout's ColumnLayout (`stackBefore`), with `panelHeightFactor` raised to keep key height. KDE's row stays hidden: Latin composers never set candidates. | Verified (strip is row 0, keys below) |
| Tap-to-swap (`wordswap.*`) | `commit(new, -bytes(old), bytes(old))` once we confirm `old` sits right before the cursor. Byte counts are UTF-8: input-method-v1 is byte-based, and the engine passes values unchanged (`src/inputmethodconnection.cpp:227`). | Verified (delete -13/13 then commit) |
| Learning (`learningmanager`, `learning.hpp`) | Unchanged. The gate reads `inputMethodHints`. | Inferred |
| Password and private-field gate | Hints are mapped from Wayland purpose/hints in `src/inputmethodhints.cpp`: hidden text → `ImhHiddenText`+`ImhSensitiveData`; password → `ImhSensitiveData`; email/url/digits/number/phone → their `Imh*Only`/`PreferNumbers`; missing completion/correction → `ImhNoPredictiveText`. This is enough for "never learn from password, e-mail, web-address or number fields". The Flatpak patch (`scripts/patches/plasma-prediction-policy.patch`) is not needed. Terminal and latin-only both become `ImhPreferLatin`. | Swipe gate verified |
| Language/layout switching | `keyboardController.layoutId` gives package and layout; `inputEngine.locale` gives the primary locale. Switch the language pack on change. `layoutType` != `"main"` means a symbols/number page, so no swipe there. | Inferred |
| Spacebar cursor slide | Same layer: `sendDirectKey(Qt.Key_Left/Right)`. Upstream MR !69 (open) adds its own version; detect it and step aside to avoid doing it twice. | Inferred |
| Settings | Keep the `swipe-keyboard` CLI and our setup guide; the KCM cannot host our page | n/a |
| Haptics/sound | `Feedback.play()` from the internal app module `org.kde.plasma.keyboard`; reachable but internal | Inferred |

Only `plugin/swipeinputmethod.{h,cpp}` (≈1,750 lines) and `plugin/SwipeCapture.qml` depend on
Qt VKBD, plus `integration/layout.py` (which patches the old layout format). All other
`plugin/` files (sessions, learning, language runtime, word swap, recorder) contain no Qt VKBD
code and should carry over.

**Lost or degraded without upstream:**
- No preedit (the underlined in-progress word), so every word is committed outright. Fixes
  then rely on `delete_surrounding_text`. Apps that send no surrounding text still apply the
  delete, but we cannot double-check what we're deleting. Rule: replace only a word we
  ourselves committed, and only if no cursor or text change arrived since. Otherwise drop the
  offer.
- No use of KDE's suggestion row, KDE's long-press-on-suggestion, or keyboard navigation of
  suggestions (`KeyboardNavigation` knows only its own row).
- The layer hooks into internals: the Keyboard item found by properties, the layout Loader
  holding an item with `panelHeightFactor`, and keys exposing `key` and `text`. Each is a
  version risk; check them at startup and stay out of the way when one is missing.

## 3. Coexistence: one package for 6.7/6.8 and 6.9

- **Package metadata:** remove the `plasma-keyboard<6.9` (Arch) and `< 1:6.9` (Fedora) upper
  bounds and keep `>=6.7`. Without this, Arch users cannot update the whole system on 6.9 day.
  Move `qt6-virtualkeyboard` into the legacy part; 6.9 no longer depends on it, but our legacy
  plugin does.
- **Ship both front ends:** `qml/SwipeKeyboard` (legacy Qt VKBD plugin, as today) and, e.g.,
  `qml/SwipeKeyboard2` (new core). Both link the same `engine/` and the shared `plugin/`
  sessions. Separate module names mean the wrong one is never loaded by accident.
- **Choose at launch by checking features, not version numbers:** new core if
  `/usr/share/plasma/keyboard/keyboardpackages` exists (or `plasma-keyboard` no longer links
  `libQt6VirtualKeyboard`); legacy if the Qt VKBD layout tree is present. Use the version only
  as a tiebreaker, and keep the existing rule: unknown means start stock.
  `setup.py check()` currently hard-fails outside 6.7/6.8 (`integration/setup.py:122`). On 6.9
  it should run the new-core checks: stock packages found, wrapper generation succeeds,
  preflight loads `SwipeKeyboard2`.
- **Upgrade day, after the fix:** pacman installs 6.9. The keyboard keeps running the old code
  until the next login or restart. At the next launch our launcher detects the new core,
  generates shadow packages and starts with swipe. If anything fails, the stock keyboard
  starts. **Separate KDE issue:** `src/qml/KeyboardPanel.qml:111` calls
  `keyboardController.layoutIdsForLocales(...)`, which `KeyboardController` does not define
  in master. A 6.8 user whose settings hold only `enabledLocales` may lose their language
  list on upgrade (inferred, not run). Our shadow packages follow whatever IDs KDE settles on.
- **Flatpak (Deck):** unaffected until we rebase it onto a 6.9 runtime. Then it gets the same
  shadow-package launcher, and the old patch is dropped.

## 4. Prototype: what I built and what it proves

Scratch build under `~/.cache/swipe-keyboard-train/` only. It did not install to `/usr`, used
no sudo, and did not touch the running keyboard. It was deleted afterwards, except the
plasma-keyboard clone. Steps:
1. Built ECM 6.30 into a scratch prefix (not installed on this machine).
2. A harness built plasma-keyboard master's real `virtualkeyboard/` library, QML components
   and `layouts/defaultplugin` **unmodified**. It ran the real `Keyboard.qml` with a fake
   compositor backend that logs commit/delete/preedit, plus stubs for the app-only
   `Feedback`/`PlasmaKeyboardSettings`. The full app needs PlasmaQuick ≥6.7.90; this machine
   has 6.7.5. Touches were synthesized with QTest, offscreen.
3. A separately built QML plugin (`org.itsdestin.swipeproto`) stood in for our add-on. It does
   not link plasma-keyboard; it reaches the engine only through properties and invokables.
   A shadow package with the same Id as KDE's English package sat in a second data directory.
4. The same steps were repeated against MR !179's branch (new `KeyboardLayoutDefinition` format).

**Verified (both master and !179):**
- The shadow package wins: `org.kde.plasma.keyboard.en/mobile-qwerty` resolved to our wrapper file.
- Our external QML module loaded inside the layout and found the Keyboard item and engine.
- Tap `q` committed `Q` (stock auto-capitals intact).
- Swipe h→e→l→o: the layer took the touch, the key typed nothing, and our commit went through
  (stand-in "recogniser" = keys crossed).
- Tap-to-swap: `delete index=-13 length=13`, then `commit 'hello '`, gave `Qhello `.
- Password hints: the layer stayed passive and the key typed `h` as stock does.
- Strip inserted as the layout's first row (33 px vs 52 px key rows at 60:100 weight).
- Stock baseline without our package: the same swipe typed just `h`.

**Found (fix in the real version):** with !179, the global hook also attached to a layout
that was still being created (the fallback desktop layout). That gave `engine=null` and
"invalid context" warnings before it attached correctly. Attach only when `layoutType=="main"`
and the layout belongs to one of our packages, and defer the attach by one event loop turn.

**Inferred, not verified:** behaviour in the real `plasma-keyboard` binary under KWin (needs
Plasma ≥6.8.80 libs: a KDE Linux VM, a nested session or the 6.9 beta); real touchscreen
timing; apps without surrounding-text support; our real engine in this bridge (it is already
a Qt plugin today, so low risk).

**Smallest next proof (≈3–4 days):** take the harness approach, then link the real `engine/`
and `swipesession`/`nextwordsession` into a `SwipeKeyboard2` bridge: a real swipe word plus
real next-word suggestions in our row. Then run it in a KDE Linux VM (or the 6.9 beta) with
the real binary.

**Full port estimate:** bridge class and swipe layer (1–1.5 wk); suggestion row,
completion/next-word, swap safety rules (1–1.5 wk); case/shift, symbols-page skip, language
switching, learning gates (0.5 wk); wrapper generator for both formats, launcher detection,
package changes, uninstall (0.5–1 wk); tests (QML harness in CI, like this prototype) (0.5 wk).
**≈4–6 weeks**, plus 1 week on the beta.

**Risks:** upstream churn (!179 today; !113 CJK, !69 space slide, !71 split layouts are
open); internal-API breakage after release (mitigated by startup checks and stock fallback);
touch takeover could behave differently on real hardware or on multi-touch (keys take 1
point each); our own row adds height on small phones; duplicate features if KDE ships
swipe or prediction (issue #5 and #77 are open). Prototype code fragments: below.

```qml
// wrapper generated into the shadow package (same dir as KDE's MobileQwerty.qml)
import SwipeKeyboard2
MobileQwerty { id: w; Component.onCompleted: SwipeHook.watch(w) }
```
```qml
// swipe layer: listen passively; past the threshold take the touch away from the key
DragHandler { target: null
    enabled: !!engine && !(engine.inputMethodHints & (Qt.ImhHiddenText | Qt.ImhSensitiveData))
    onActiveChanged: /* active: start path; inactive: recognise, engine.commit(word + " ") */ {} }
```

## 5. Licensing and process notes for later upstreaming

- New-core files are `GPL-2.0-only OR GPL-3.0-only OR LicenseRef-KDE-Accepted-GPL`; CMake
  files are BSD-2-Clause; REUSE-linted in CI. Qt VKBD's GPL-3-only constraint goes away with
  !109. Our roadmap's licence decision (KDE triple for keyboard code, LGPL triple for the
  engine) fits.
- CI: clang-format, qmllint, reuse-lint; Linux/Alpine/FreeBSD Qt6 builds. New dependencies
  must be optional. Qt ≥6.11, KF6 ≥6.30 today; the 6.9 table lists Qt 6.12 / KF 6.34.
- i18n: `i18n()` in C++/QML; `Messages.sh`; `po/` synced by l10n bots; layout names
  translated in `metadata.json`.
- Upstream would want swipe as a composer plus layout components, not a wrapper. The
  wrapper/hook is our bridge until then; keep `engine/` and the sessions independent of
  either integration so they can go upstream as they are.
- Open threads to reference: issue #5 "Discussion: Swipe support" (updated 2026-10-19),
  issue #77 "Presage based word prediction" (composer plan), MR !179 (layout definition).
  The maintainers have not been contacted.
- Arch `extra` already has plasma-keyboard 6.8.1 (2026-10-21); this machine is on 6.7.5.
  Arch usually packages Plasma releases within days, so expect 6.9 there in late February 2027.
